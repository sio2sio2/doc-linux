.. _kea:

Kea |DHCP|
**********
El `servidor Kea <https://www.isc.org/kea/>`_ es el remplazo del |ISC| para
:ref:`su antiguo servidor <isc-dhcp>`, cuyo desarrollo abandonó definitivamente en 2022.
Tiene un diseño modular más moderno y permite el almacenamiento de asignaciones
en bases de datos.

Ilustremos su configuración para el mismo servidor que ya hemos ido estudiando:
uno que tiene una interfaz externa a través de la cual no queremos proporcionar
configuraciones de red y dos interfaces internas a través de las que sí:

.. code-block:: none

   # Interfaz externa.
   allow-hotplug eth0
   iface eth0 inet dhcp

   # Red interna 1 (interna1.local)
   allow-hotplug eth1
   iface eth1 inet static
      address 192.168.255.1/24

   # Red interna 2 (interna2.local)
   allow-hotplug eth2
   iface eth2 inet static
      address 192.168.254.1/24

*Debian* separa los módulos del servidor en distintos paquetes. Como, en
principio, sólo nos interesa aprender cómo se configura de forma básica para
|IP|\ v4:

.. code-block:: console

   # apt install kea-dhcp4-server

Configuración básica
====================
La configuración del servidor se encuentra toda dentro del directorio
:file:`/etc/kea` y es ahí donde debemos crear los archivos de configuración.
Debe crearse un archivo independiente por cada módulo del servidor (p.ej. un
archivo para el módulo encargado de |IP|\ v4 y otro distinto para el módulo
encargado de |IP|\ v6) y, en teoría, los nombres son arbitrarios. Sin embargo,
la configuración del servicio en *Debian* está pensada para que en el caso del
módulo para |IP|\ v4 el nombre del archivo sea :file:`kea-dhcp4.conf` (que por
otro lado el nombre que suele asignarse por convención).

Así pues comencemos por una configuración muy, muy básica con la que se
proporciona configuraciones a una red sin distinguir máquinas clientes:

.. literalinclude:: files/kea-dhcp4.simple.conf
   :language: json

Las claves son las siguientes:

* Los archivos de configuración están en formato |JSON|\ [#]_.
* La propiedad de nivel superior que gestiona este módulo es *Dhcp4*.
* Sus propiedades hijas podemos clasificarlas en cuatro tipos:

  a. Algunas que afectan al funcionamiento del propio módulo como
     *interfaces-config* y *lease-database* y que, por tanto, sólo pueden
     definirse en este ámbito global.

  #. Características del servicio |DHCP| como si es autoritario o cuál
     es el tiempo máximo de concesión. Éstas sí pueden ser sobrescritas por una
     configuración específica en una subred.

  #. Opciones |DHCP| que se aplicarán a todas las redes y que se introducen con
     *option-data*. También pueden ser sobreeescritas.

  #. La propiedad *subnet* que permite definir cada una de las redes en las
     que actuará el servidor.

* En cada subred debemos definir varios aspectos:

  - Un identificador obligatorio (un número entero de 4 *bytes*).
  - Cuál es la subred en formato |CIDR|.
  - Las características del servicio |DHCP| que queremos que sobreescriban los
    valores globales (en la configuración de ejemplo no hay).
  - Las opciones |DHCP| particulares para la subred que sobrescribirán cualquier
    valor global.
  - Los distintos *pools* de asignación. Para definir el rango, se puede usar la
    notación utilizada en el archivo o una notación |CIDR|: "``192.168.255.32/26``".

* Como podemos ver, características del servicio y opciones |DHCP| pueden definirse
  en distinto nivel, así que conviene saber cuál es la prioridad (de mayor a menor):

  a. :ref:`Reservas de máquinas <kea-reservations>`.
  #. *Pools*.
  #. Subredes.
  #. Red compartida.
  #. :ref:`Clases <kea-classes>`
  #. Nivel global.

  Ya iremos aprendiendo qué son algunos de estos niveles que no hemos introducido aún.

.. tip:: Una propiedad muy útil (definible a nivel global o de subred) es:

   .. code-block:: json

      "match-client-id": false

   que evita que el servidor identifique al cliente por el identificador que
   éste le envía (opcion |DHCP| 61) y los identifique por su dirección |MAC|.
   Esta opción es muy útil en escenarios en los que los clientes están
   configurados para arrancar primero por red y pueden, si no se configura esta
   propiedad, llegar a consumir dos direcciones |IP|: una este arranque por red
   y, fallado éste, otra la del sistema operativo local, ya que ambas peticiones
   se identifican de distinto modo.

Una vez escrito el archivo de configuración, puede comprobarse a mano su validez
con:

.. code-block:: console

   # kea-dhcp4 -t kea-dhcp4.conf

.. caution:: En *Debian* el servicio está asegurado por :ref:`Apparmor
   <apparmor>` y el acceso al directorio de configuración :file:`/etc/kea` está
   restringido al usuario y grupo *_kea*. Esto supone que la prueba, que se hace
   como administrador, fallará por falta de permisos. Para evitarlo, podemos
   ejecutar la prueba con el usuario apropiado:

   .. code-block:: console

      # runuser -u _kea -- kea-dhcp4 -t kea-dhcp4.conf

   o bien, si prevemos hacer más pruebas y no queremos usar continuamente
   :ref:`runuser`:

   .. code-block:: console

      # newgrp _kea  # root pertenecerá temporalmente al grupo _kea.
      # kea-dhcp4 -t kea-dhcp4.conf

Por último, es conveniente saber cómo consultarle al servidor las asignaciones
que ha realizado. Sin necesidad de instalar servicios adicionales, se puede,
simplemente consultar el |CSV| de asignaciones:

.. _kea-reservations:

Reservas de máquinas
====================
Podemos identificar máquinas conocidas mediante distintos criterios (como su
identificador de cliente o su dirección |MAC|) para definirles alguna opción
|DHCP|, incluida una dirección |IP|. Para ello, debemos incluir un array *reservations*
dentro de alguna de las subredes:


.. code-block:: json

   {
      "subnet4": [
         {
            "id": 1,
            "subnet": "182.168.255.0/24",

            // ...

            "reservations": [
               {"hw-address": "de:ad:be:ef:00:11"},
               {"hw-address": "de:ad:be:ef:00:12"}
            ]
         }
      ]
   }

En este caso hemos declarado dos máquinas identificadas por su dirección |MAC|,
aunque no hemos definido qué opciones |DHCP| particulares tiene cada una de
ellas. ¿Tiene algún sentido? Sí, porque el servidor predefine dos :ref:`clases
de máquinas <kea-classes>` (``KNOWN`` y ``UNKNOW``), pero ya veremos cómo tratar
esto. Por ahora, limitémonos a definir opciones particulares para estas
másquinas identificadas:

.. code-block:: json

   {
      "reservations" : [
         {
            "hw-address": "de:ad:be:ef:00:11",
            "ip-address": "192.168.255.10",  // Fuera del rango.
            "option-data": [
               {
                  "name": "dhcp-lease-time", 
                  "data": 86400 // Un día entero.
               } 
            ]
         },
         {
            "hw-address": "de:ad:be:ef:00:12",
            "ip-address": "192.168.255.32"  // Dentro de un pool definido.
         }
      ]
   }

Como puede verse es válido asignar |IP| que estén incluidas en algún rango de
asignación que definamos con *pool*. Sin embargo, esto implica hacer más
comprobaciones, por lo que mejora el rendimiento del servidor que lo evitemos y
declaremos explícitamente en la definición de la subred o en a nivel global que
nuestras definiciones serán siempre fuera de los rangos establecidos:

.. code-block:: json

   {
      "subnet4": [
         {
            "id": 1,
            "subnet": "182.168.255.0/24",
            "reservations-out-of-pool": true,

            // ...

            "reservations": [
               {
                  "hw-address": "de:ad:be:ef:00:11",
                  "ip-address": "192.168.255.10"
               },
               {
                  "hw-address": "de:ad:be:ef:00:12",
                  "ip-address": "192.168.255.10"
               }
            ]
         }
      ]
   }

Lo habitual es que la identificación de máquinas se realice a nivel de subred,
que es lo que hemos hecho hasta ahora. Sin embargo, puede ocurrir que nos
interese identificar algunas máquinas a nivel global (p.ej. portátiles que se
conectan a distintas redes). Para ello necesitamos, no sólo escribir un bloque
*reservations* en fuera de las subredes, sino habilitar explícitamente las
reservas globales:

.. code-block:: json
   :emphasize-lines: 3

   {
      "Dhcp4": {
         "reservations-global": true,  // Habilitamos reservas globales
         "reservations": [             // Bloque global
            {
               "hw-address": "de:ad:be:ef:12:34",
               "option-data": [
                  {
                     "name": "dhcp-lease-time",
                     "data": 3600
                  }
               ]
            }
         ],

         // ... Resto de configuración (incluidas subredes) ...
      }
   }

Obviamente, si las reservas son globales, no tiene sentido definir opciones que
sean propias de alguna subred (como una dirección |IP| fija).

.. _kea-classes:

Clases
======
Las clases permiten agrupar clientes por alguna de sus características, a fin de
asignarles un rango particular de asignación o unas opciones |DHCP| distintas al
resto. Antes de ver cómo definirlas es conveniente que sepamos que ya existen
algunas clases predefinidas:

``ALL``
   que es la clase que engloba a todos los clientes.

``KNOWN``
   que es la clase que engloba a todas aquellas máquinas que han sido definidas
   usando lo explicado bajo el epígrafe anterior.

``UNKNOWN``
   que es la clase complementaria a la anterior.

Para definir una clase hay que hacerlo en el nivel global:

.. code-block:: json

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "virtualbox",
               "test": "substring(pkt4.mac, 0, 3) == 0x080027"
            }
         ]
      }
   }

.. caution:: A diferencia de lo que ocurre con el servidor |ISC| |DHCP|, el
   campo que contiene la |MAC| es estrictamente la |MAC| y no contiene en su
   primer *byte* el tipo de red.

Cuando se quiere comprobar una opción |DHCP| debe hacerse lo siguiente:

.. code-block:: json
   :emphasize-lines: 6

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "pxe",
               "test": "substring(option[60].hex, 0, 9) == 'PXEClient'"
            }
         ],
         // ...
      }
   }

En este caso, nos hemos centrado en la opción **60** (*Vendor Class*), que
identifica al tipo de dispositivo. Por tanto, la clase identifica a las máquinas
que han arrancado por red (|PXE|).

.. note:: Obsérvese que en este caso la cadena se ha escrito entre comillas para
   que la comparación sea de caracteres. En el caso anterior de la |MAC| nos
   interesaba directamente el código hexadecimal, por lo que añadimos el prefijo
   "*0x*" y no usamos comillas.

Las opciones permiten incluir los operadores lógicos *and*, *or* y *not* para
crear operaciones más complejas:

.. code-block:: json
   :emphasize-lines: 7

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "pxe_win",
               // PXE o clientes Windows.
               "test": "substring(option[60].hex, 0, 9) == 'PXEClient' or substring(option[60].hex, 0, 8) == 'MSFT 5.0'"
            }
         ]
      }
   }

La precedencia de estos operadores es la habitual y pueden usarse parántesis
para modificarla.

Como condición podemos incluir en *test*  la pertenecia a otra clase:

.. code-block:: json
   :emphasize-lines: 10

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "pxe",
               "test": "substring(option[60].hex, 0, 9) == 'PXEClient'"
            },
            {
               "name": "not-pxe",
               "test": "not member('pxe')"
            }
         ],
         // ...
      }
   }

Sin embargo, es muy importante tener presente que para que funcione la clase
referida debe haberse definido antes.

Un uso típico de las clases es asignarle algún *pool* específico. Por ejemplo:

.. code-block:: json

   {
      // ...
      "subnet4": [
         {
            "subnet": "192.168.255.0/24",
            "id": 1,
            "pools": [
               {
                  "pool": "192.168.255.32/27",
                  "client-classes": [ "pxe" ]
               },
               {
                  "pool": "192.168.255.64/26",
                  "client-classes": [ "not-pxe" ]
               }
            ]
         }
      ]
   }

.. note:: Téngase presente que en este servidor no hay un equivalente al ``deny
   members of`` del :ref:`ISC DHCP <isc-dhcp>`, por lo que emular este
   comportamiento implica definir la clase complementaria como hemos hecho.

Cuando se define una clase, también se pueden añadir características del
servidor u opciones |DHCP| que sean aplicables a los miembros de la clase. Por
ejemplo:

.. code-block::

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "pxe",
               "test": "substring(option[60].hex, 0, 9) == 'PXEClient'",
               "max-valid-lifetime": 3600
            }
         ]
         // ...
      }
   }

.. warning:: Tenga presente la prioridad. En este caso, cualquier redefinición
   de ese tiempo máximo de concesión dentro de una subred, por ejemplo,
   sobreescribirá la definición en la clase. Sin embargo, esto puede cambiar si
   se retrasa la evaluación, como se verá a continuación.

.. caution:: Las clases se evalúan antes de la selección de la red y la
   evaluación de las reservas, pero es posible alterar este comportamiento para
   que se evalúen después:

   .. code-block:: json
      :emphasize-lines: 7, 17

      {
         "Dhcp4": {
            "client-classes": [
               {
                  "name": "reservadas",
                  "test": "member('KNOWN')",
                  "only-in-additional-list": true,
                  "option-data": [
                     // Definición de algunas opciones.
                  ] 
               }
            ],
            "subnet4": [
               {
                  "subnet": "192.168.255.0/24",
                  "id": 1,
                  "evaluate-additional-classes": [ "reservadas" ],
                  // ...
               }
            ]
         }
      }

   En este caso, no es necesario indicarlo, porque las clases ``KNOWN`` y
   ``UNKNOWN`` son especiales y *Kea* ya tiene en cuenta que debe definirlas
   después de la reserva de máquinas. Sin embargo, posponer la evaluación de
   la clase provoca que la evaluación (que podría ser mucho más complicada)
   se haga ya seleccionada la red y sólo para la **1** con lo que si hubiera
   más redes, nos ahorraríamos la evaluación para todas ellas lo que mejora
   el rendimiento.

   Téngase presente que al retrasar la evaluación de la clase, también se
   altera la prioridad: las características del servicio y las opciones
   |DHCP| definidas para la clase tomarán prioridad sobre las definidas para
   la subred. E incluso sobre las definidas para el *pool* si la propiedad
   ``evaluate-additional-classes`` se inncluye dentro de la declaración de un
   *pool* y no dentro de la declaración de la subred.

Otra posibilidad relacionada con las clases es añadir particularmente una
reserva a una o varias clases ya definidas.

.. code-block:: json

   {
      "Dhcp4": {
         "client-classes": [
            {
               "name": "selecta"
            }
         ],
         // ...
         "subnet4": [
            {
               "subnet": "192.168.255.0/4",
               "id": 1,
               // ...
               "reservations": [
                  {
                     "hw-address": "de:ad:be:ef:01:23",
                     "client-classes": [ "selecta" ]
                  }
               ]
            },
            // ...
         ]

      }
   }

En este caso, hemos dejado la declaración de la clase sin establecer una
condición con ``test``, porque nuestra intención es que pertenezcan a la clase
exclusivamente las máquinas referenciadas que seleccionemos. Sin embargo, podría
haberse incluido alguna condición y, en ese caso, la clase estaría constituida
por todas los clientes que cumplieran con la condición más las reservas que
hubiéramos explicitamente incluido, cumplan o no la condición.

Depuración
==========
Es importante saber cómo consultar qué está recibiendo el cliente y qué está
recibiendo y enviando el servidor para saber si nuestra configuración funciona
como creemos que debería funcionar.

Las estrategias son las siguientes:

a. Comprobar qué concesión recibe el cliente, lo cual dependerá de :ref:`cuál
   sea el cliente concreto <DHCP-clients>`.

#. Consultar las concesiones del servidor, que en el caso de que usemos la
   predeterminada (*memfile*), consiste en consultar
   el archivo |CSV|:

   .. code-block:: console

      # column -ts, /var/lib/kea/kea-leases4.csv

#. Consultar qué paquetes envía y recibe el servidor. Para ello, debemos configurar
   los registros que escribe el servidor, ya que por defecto sólo se registran
   hasta el nivel *INFO*. Para variar este comportamiento, podemos añadir:

   .. code-block:: json

      {
         "Dhcp4": {
            // ...
            "loggers": [
               {
                  "name": "kea-dhcp4.packets",
                  "severity": "DEBUG",
                  "debuglevel": 55,
                  "output_options": [{"output": "syslog"}]
               }
            ]
         }
      }

   que lo que hace es cambiar la configuración del componente que se encarga de
   escribir los paquetes recibidos y enviados por :program:`Kea`, ya que el
   nivel raíz (*kea-dhcp4*) no escribe mensajes de depuración. Además, pasamos
   esos mensajes al demonio de *syslog* que en las versiones modernas de *Debian*
   acaba gestionando :ref:`SystemD <systemd>`. Por tanto, para revisar al vuelo los
   paquetes basta con hacer:

   .. code-block:: console

      # journalctl -u kea-dhcp4-server -n5 -f

   y generar peticiones con el cliente.
