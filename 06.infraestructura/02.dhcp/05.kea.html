6.1.5. Kea DHCP¶

El servidor Kea es el remplazo del ISC para su antiguo servidor, cuyo desarrollo abandonó definitivamente en 2022. Tiene un diseño modular más moderno y permite el almacenamiento de asignaciones en bases de datos.

Ilustremos su configuración para el mismo servidor que ya hemos ido estudiando: uno que tiene una interfaz externa a través de la cual no queremos proporcionar configuraciones de red y dos interfaces internas a través de las que sí:

# Interfaz externa.
allow-hotplug eth0
iface eth0 inet dhcp

# Red interna 1 (interna1.local)
allow-hotplug eth1
iface eth1 inet static
   address 192.168.255.1/24

# Red interna 2 (interna2.local)
allow-hotplug eth2
iface eth2 inet static
   address 192.168.254.1/24

Debian separa los módulos del servidor en distintos paquetes. Como, en principio, sólo nos interesa aprender cómo se configura de forma básica para IPv4:

# apt install kea-dhcp4-server

6.1.5.1. Configuración básica¶

La configuración del servidor se encuentra toda dentro del directorio /etc/kea y es ahí donde debemos crear los archivos de configuración. Debe crearse un archivo independiente por cada módulo del servidor (p.ej. un archivo para el módulo encargado de IPv4 y otro distinto para el módulo encargado de IPv6) y, en teoría, los nombres son arbitrarios. Sin embargo, la configuración del servicio en Debian está pensada para que en el caso del módulo para IPv4 el nombre del archivo sea kea-dhcp4.conf (que por otro lado el nombre que suele asignarse por convención).

Así pues comencemos por una configuración muy, muy básica con la que se proporciona configuraciones a una red sin distinguir máquinas clientes:

{
   "Dhcp4": {
      "interfaces-config": {
          # Intefaces por las que se proporciona configuración de red
         "interfaces": [ "eth1" ]
      },

      # Almacenamiento de las asignaciones (sin base de datos: CSV)
      "lease-database": {
         "type": "memfile",
         "persist": true
      },

      # -- Parámetro globales
      "authoritative": true,
      "valid-lifetime": 6000,
      "max-valid-lifetime": 7200,

      # -- Opciones DHCP aplicables a todas la redes
      "option-data": [
         {
            "name": "ntp-servers",
            "data": "150.214.94.5"  # La IP de hora.roa.es
         }
      ],

      # -- Configuración de subredes
      "subnet4": [
         {
            "id": 1,
            "subnet": "192.168.255.0/24",
            # Opciones DHCP específicas de esta subred
            "option-data": [
               {
                  "name": "routers",
                  "data": "192.168.255.1"
               },
               {
                  "name": "domain-name-servers",
                  "data": "192.168.255.1"  # Para varios se separa por comas.
               },
               {
                  "name": "domain-name",
                  "data": "smr2.test"
               },
               {
                  "name": "broadcast-address",
                  "data": "192.168.255.255"
               }
            ],
            # Pools de asignaciones.
            "pools": [
               {
                  #"pool": "192.168.255.32 - 192.168.255.63"
                  "pool": "192.168.255.32/27"
               }
            ]
         }
      ]
   }
}

Las claves son las siguientes:

  • Los archivos de configuración están en formato JSON[1].

  • La propiedad de nivel superior que gestiona este módulo es Dhcp4.

  • Sus propiedades hijas podemos clasificarlas en cuatro tipos:

    1. Algunas que afectan al funcionamiento del propio módulo como interfaces-config y lease-database y que, por tanto, sólo pueden definirse en este ámbito global.

    2. Características del servicio DHCP como si es autoritario o cuál es el tiempo máximo de concesión. Éstas sí pueden ser sobrescritas por una configuración específica en una subred.

    3. Opciones DHCP que se aplicarán a todas las redes y que se introducen con option-data. También pueden ser sobreeescritas.

    4. La propiedad subnet que permite definir cada una de las redes en las que actuará el servidor.

  • En cada subred debemos definir varios aspectos:

    • Un identificador obligatorio (un número entero de 4 bytes).

    • Cuál es la subred en formato CIDR.

    • Las características del servicio DHCP que queremos que sobreescriban los valores globales (en la configuración de ejemplo no hay).

    • Las opciones DHCP particulares para la subred que sobrescribirán cualquier valor global.

    • Los distintos pools de asignación. Para definir el rango, se puede usar la notación utilizada en el archivo o una notación CIDR: «192.168.255.32/26».

Truco

Una propiedad muy útil (definible a nivel global o de subred) es:

"match-client-id": false

que evita que el servidor identifique al cliente por el identificador que éste le envía (opcion DHCP 61) y los identifique por su dirección MAC. Esta opción es muy útil en escenarios en los que los clientes están configurados para arrancar primero por red y pueden, si no se configura esta propiedad, llegar a consumir dos direcciones IP: una este arranque por red y, fallado éste, otra la del sistema operativo local, ya que ambas peticiones se identifican de distinto modo.

Una vez escrito el archivo de configuración, puede comprobarse a mano su validez con:

# kea-dhcp4 -t kea-dhcp4.conf

Prudencia

En Debian el servicio está asegurado por Apparmor y el acceso al directorio de configuración /etc/kea está restringido al usuario y grupo _kea. Esto supone que la prueba, que se hace como administrador, fallará por falta de permisos. Para evitarlo, podemos ejecutar la prueba con el usuario apropiado:

# runuser -u _kea -- kea-dhcp4 -t kea-dhcp4.conf

o bien, si prevemos hacer más pruebas y no queremos usar continuamente runuser:

# newgrp _kea  # root pertenecerá temporalmente al grupo _kea.
# kea-dhcp4 -t kea-dhcp4.conf

Por último, es conveniente saber cómo consultarle al servidor las asignaciones que ha realizado. Sin necesidad de instalar servicios adicionales, se puede, simplemente consultar el CSV de asignaciones:

# column -ts, /var/lib/kea/kea-leases4.csv

6.1.5.2. Declaración de máquinas¶

Podemos identificar máquinas conocidas mediante distintos criterios (como su identificador de cliente o su dirección MAC) para definirles alguna opción DHCP, incluida una dirección IP. Para ello, debemos incluir un array reservations dentro de alguna de las subredes:

{
   "subnet4": [
      {
         "id": 1,
         "subnet": "182.168.255.0/24",

         // ...

         "reservations": [
            {"hw-address": "de:ad:be:ef:00:11"},
            {"hw-address": "de:ad:be:ef:00:12"}
         ]
      }
   ]
}

En este caso hemos declarado dos máquinas identificadas por su dirección MAC, aunque no hemos definido qué opciones DHCP particulares tiene cada una de ellas. ¿Tiene algún sentido? Sí, porque el servidor predefine dos clases de máquinas (KNOWN y UNKNOW), pero ya veremos cómo tratar esto. Por ahora, limitémonos a definir opciones particulares para estas másquinas identificadas:

{
   "reservations" : [
      {
         "hw-address": "de:ad:be:ef:00:11",
         "ip-address": "192.168.255.10",  // Fuera del rango.
         "option-data": [
            {
               "name": "dhcp-lease-time",
               "data": 86400 // Un día entero.
            }
         ]
      },
      {
         "hw-address": "de:ad:be:ef:00:12",
         "ip-address": "192.168.255.32"  // Dentro de un pool definido.
      }
   ]
}

Como puede verse es válido asignar IP que estén incluidas en algún rango de asignación que definamos con pool. Sin embargo, esto implica hacer más comprobaciones, por lo que mejora el rendimiento del servidor que lo evitemos y declaremos explícitamente en la definición de la subred o en a nivel global que nuestras definiciones serán siempre fuera de los rangos establecidos:

{
   "subnet4": [
      {
         "id": 1,
         "subnet": "182.168.255.0/24",
         "reservations-out-of-pool": true,

         // ...

         "reservations": [
            {
               "hw-address": "de:ad:be:ef:00:11",
               "ip-address": "192.168.255.10"
            },
            {
               "hw-address": "de:ad:be:ef:00:12",
               "ip-address": "192.168.255.10"
            }
         ]
      }
   ]
}

Lo habitual es que la identificación de máquinas se realice a nivel de subred, que es lo que hemos hecho hasta ahora. Sin embargo, puede ocurrir que nos interese identificar algunas máquinas a nivel global (p.ej. portátiles que se conectan a distintas redes). Para ello necesitamos, no sólo escribir un bloque reservations en fuera de las subredes, sino habilitar explícitamente las reservas globales:

{
   "Dhcp4": {
      "reservations-global": true,  // Habilitamos reservas globales
      "reservations": [             // Bloque global
         {
            "hw-address": "de:ad:be:ef:12:34",
            "option-data": [
               {
                  "name": "dhcp-lease-time",
                  "data": 3600
               }
            ]
         }
      ],

      // ... Resto de configuración (incluidas subredes) ...
   }
}

Obviamente, si las reservas son globales, no tiene sentido definir opciones que sean propias de alguna subred (como una dirección IP fija).

6.1.5.3. Clases¶

Las clases permiten agrupar clientes por alguna de sus características, a fin de asignarles un rango particular de asignación o unas opciones DHCP distintas al resto. Antes de ver cómo definirlas es conveniente que sepamos que ya existen algunas clases predefinidas:

ALL

que es la clase que engloba a todos los clientes.

KNOWN

que es la clase que engloba a todas aquellas máquinas que han sido definidas usando lo explicado bajo el epígrafe anterior.

UNKNOWN

que es la clase complementaria a la anterior.

Para definir una clase hay que hacerlo en el nivel global:

{
   "Dhcp4": {
      "client-classes": [
         {
            "name": "virtualbox",
            "test": "substring(pkt4.mac, 0, 3) == 0x080027"
         }
      ]
   }
}

Prudencia

A diferencia de lo que ocurre con el servidor ISC DHCP, el campo que contiene la MAC es estrictamente la MAC y no contiene en su primer byte el tipo de red.

Cuando se quiere comprobar una opción DHCP debe hacerse lo siguiente:

{
   "Dhcp4": {
      "client-classes": [
         {
            "name": "virtualbox",
            "test": "substring(option[60].hex, 0, 9) == 'PXEClient'"
         }
      ]
   }
}

En este caso, nos hemos centrado en la opción 60 (Vendor Class), que identifica al tipo de dispositivo. Por tanto, la clase identifica a las máquinas que han arrancado por red (PXE).

Nota

Obsérvese que en este caso la cadena se ha escrito entre comillas para que la comparación sea de caracteres. En el caso anterior de la MAC nos interesaba directamente el código hexadecimal, por lo que añadimos el prefijo «0x» y no usamos comillas.

Las opciones permiten incluir los operadores lógicos and, or y not para crear operaciones más complejas:

{
   "Dhcp4": {
      "client-classes": [
         {
            "name": "virtualbox",
            // PXE o clientes Windows.
            "test": "substring(option[60].hex, 0, 9) == 'PXEClient' or substring(option[60].hex, 0, 8) == 'MSFT 5.0'"
         }
      ]
   }
}

La precedencia de estos operadores es la habitual y pueden usarse parántesis para modificarla.

Notas al pie

[1]

En realidad, en un formato JSON relajado, ya que se admiten comentarios (también con el caracter “#”) y comas finales como los que podemos encontrar en los archivos de configuración de Visual Studio Code.
